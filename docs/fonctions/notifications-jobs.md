# Notifications (push web, push natif, email), fenêtre d'activation, jobs automatiques

> Période : 3 sept. → 19 oct. 2026. Déplacé tel quel depuis `CLAUDE.md` le 20 oct. 2026 (version du commit 7738a11). Les règles à retenir sont résumées dans `CLAUDE.md` ; ce fichier garde le détail. Quand une session modifie cette fonction, elle met ce document à jour.

### Notifications
- **Push web** : Web Push (VAPID) via `lib/pushHelper.js` (`sendToSubscriptions` : lots de 50 en parallèle, timeout 10 s, abonnements 410/404 supprimés), service worker `public/sw.js`. VAPID est configuré une seule fois dans `pushHelper.js` : les routes et jobs passent par ses fonctions
- **Push natif** (`dhomebarber-api/lib/nativePush.js`, ajouté le 5 sept. 2026, release v74) : token enregistré via `subscribe-native` (endpoint `native://<platform>/<token>`), déclenché par `src/lib/pushNotifications.js` sur iOS/Android. `sendToSubscriptions` route désormais ces endpoints vers **APNs** (iOS, le jeton de `@capacitor/push-notifications` est un jeton APNs brut) et **FCM HTTP v1** (Android). Aucune dépendance npm ajoutée : `node:http2`, `node:crypto` et `fetch` suffisent.
  - APNs : JWT ES256 signé avec la clé `.p8`, mis en cache 40 min (Apple refuse un rafraîchissement plus fréquent que 20 min et un jeton de plus d'1 h), une session HTTP/2 par lot, en-têtes `apns-topic` = bundle id et `apns-push-type: alert`. Un `410`, `Unregistered` ou `BadDeviceToken` supprime l'abonnement
  - FCM : JWT RS256 du compte de service échangé contre un jeton OAuth mis en cache jusqu'à expiration, envoi par lots de 50 en parallèle. Un `404`, `UNREGISTERED` ou `INVALID_ARGUMENT` supprime l'abonnement
  - **Android : activé le 5 sept. 2026** (Heroku v83). Compte de service dédié `fcm-sender@d-home-barber.iam.gserviceaccount.com`, avec le seul rôle *Administrateur de l'API Firebase Cloud Messaging* — il ne peut rien faire d'autre dans le projet. Clé posée en `FCM_SERVICE_ACCOUNT` (copie locale hors git : `~/.fcm-key/dhomebarber-fcm.json`, chmod 600). Vérifié avant déploiement : l'échange OAuth aboutit et FCM traite la requête (un faux jeton revient en `UNREGISTERED`, pas en 401). **Aucun appareil Android n'est encore abonné** : la réception réelle reste à confirmer avec un téléphone sur lequel l'app est installée et les notifications acceptées
  - **Variables à poser sur Heroku pour l'activer** — iOS : `APNS_KEY_P8` (contenu de la clé, les `\n` littéraux sont acceptés), `APNS_KEY_ID`, `APNS_TEAM_ID` (`3NXH4CTJM3`), `APNS_BUNDLE_ID` (`fr.dhomebarber.app`), optionnel `APNS_ENV=sandbox` pour tester en développement ; Android : `FCM_SERVICE_ACCOUNT` (le JSON du compte de service sur une ligne) ou `FCM_PROJECT_ID` + `FCM_CLIENT_EMAIL` + `FCM_PRIVATE_KEY`. **Sans ces variables le comportement est strictement identique à avant** : les endpoints natifs sont comptés dans `skippedNative`, rien n'est envoyé. La clé APNs se crée dans Apple Developer → Certificates, Identifiers & Profiles → Keys (type *Apple Push Notifications service*) ; elle n'a rien à voir avec la clé App Store Connect K79WY8DX6N
  - **iOS : activé le 7 oct. 2026** (Heroku v99). Clé « DHomeBarber Push », **Key ID `9Q52VPGNPL`**, environnement *Sandbox & Production*, *Team Scoped (All Topics)* (réglages définitifs chez Apple), créée dans le portail Apple Developer piloté en CDP. Fichier `~/.appstoreconnect/apns/AuthKey_9Q52VPGNPL.p8` (chmod 600) + copies dans `DHomeBarber-keystore-backup/apns/` (Documents et iCloud Drive) — Apple ne permet de le télécharger qu'une fois. Variables posées : `APNS_KEY_P8`, `APNS_KEY_ID`, `APNS_TEAM_ID`, `APNS_BUNDLE_ID` (pas d'`APNS_ENV` : production, qui sert aussi TestFlight). Vérifié : un faux jeton revient `BadDeviceToken` (clé acceptée) en production comme en sandbox, et depuis le dyno `sendToNativeEndpoints` le classe en jeton périmé. L'app avait déjà tout le reste (capacité `PUSH_NOTIFICATIONS` du bundle, `aps-environment = production` dans `App.entitlements`, profil App Store actif). **Au 7 oct., aucun iPhone n'est encore abonné** (`push_subscriptions` : 1 Android, 2 web) : réception réelle à confirmer sur un iPhone connecté avec les notifications acceptées
  - **Cause trouvée le 17 oct. 2026 : aucun iPhone ne pouvait s'abonner.** Au 17 oct. : 47 abonnements Android clients (30 comptes ; tous acceptés par FCM en `validate_only` d'après la vérification du jour), **0 iOS**, 4 web (1 client, 2 barbers, 1 admin). `ios/App/App/AppDelegate.swift` (hors git) n'avait pas les deux méthodes exigées par le README iOS de `@capacitor/push-notifications` : `didRegisterForRemoteNotificationsWithDeviceToken` → `NotificationCenter.default.post(name: .capacitorDidRegisterForRemoteNotifications, object: deviceToken)` et `didFailToRegisterForRemoteNotificationsWithError` → `.capacitorDidFailToRegisterForRemoteNotifications`. Sans elles le jeton APNs n'arrive jamais au plugin et `register()` ne répond pas. **Ajoutées localement le 17 oct.** (compilation simulateur Debug réussie) ; entitlements (`aps-environment = production`, Debug et Release) et `UIBackgroundModes` `remote-notification` étaient déjà en place. **Les iPhone ne recevront rien avant un nouveau build iOS (build 12) publié** ; à vérifier ensuite sur un vrai iPhone (ligne `native://ios/…` dans `push_subscriptions`). Ne jamais régénérer `ios/` sans reporter ces deux méthodes
  - **État au 19 oct. 2026 (soir)**, après la mise en ligne d'iOS 1.0.6 (build 13) : 43 abonnements Android clients (34 comptes) **tous valides** (FCM `validate_only`, aucun envoi), **3 iOS** (premiers abonnements iPhone, arrivés le jour même), web : admin 3, barbers 2 (Kevin le 12 oct., Sacha). Sur 316 comptes clients, ~37 seulement reçoivent quelque chose : les iPhone ne pouvaient pas s'abonner avant ce build, et chacun doit d'abord mettre l'app à jour. **Aucun barber n'est abonné dans l'app** : comptes barbers Dom (compte nommé « DhomeBarber »), Romain (« DimiShop ») et Kevin, rattachés à leur fiche ; Dom et Romain sans aucun abonnement, Kevin un abonnement web du 12 oct. seulement, et aucun des trois n'a ouvert une version avec la mesure d'audience (build 13 ou site) depuis le 18 oct. Leurs pushs « Nouveau RDV » ne partent donc vers aucun téléphone tant qu'ils n'ont pas mis l'app à jour et accepté les notifications. Les envois réussis ne sont pas journalisés (seuls les refus d'APNs / FCM le sont) : pour un essai, Admin → Notifications → « Client spécifique » vers son propre compte
  - `isConfigured()` de `pushHelper` est vrai dès qu'**un** transport est disponible (VAPID, APNs ou FCM), ce qui débloque les jobs même sans VAPID
- **Email** : Nodemailer SMTP (`lib/emailHelper.js`), silencieux si `SMTP_*` absents (`isConfigured`). Envoyé à l'inscription, création/rappel/annulation de RDV, commande, demande/devis/acceptation/refus d'événement, demande d'avis, anniversaire

### Jobs automatiques (node-cron)
- **appointmentReminder** : toutes les 30 min. Depuis le 7 oct. 2026 (v97) : rappel **la veille à l'heure du RDV**, ramenée entre 8 h et 20 h 30 (« demain jeudi 8 octobre à 16:00 ») ; RDV pris moins de 24 h avant : rappel 3 h avant, au plus tôt à 8 h, jamais à moins de 1 h 30 du RDV ni dans les 2 h qui suivent la réservation (« aujourd'hui à 16:00 ») ; **jamais entre 21 h et 8 h**. Flag `reminder_sent` posé avant l'envoi (`UPDATE … RETURNING`). Avant : fenêtre 11–12 h 30, d'où des pushs « demain » partis à 5 h pour le jour même. **Depuis le 18 oct. 2026 (v131)**, avec un délai d'annulation (`salon_settings.cancellation_hours`, 24 h) : rappel à **début − (délai + 2 h)**, ramené entre 8 h et 20 h 30 (avant 8 h : 8 h si c'est encore au moins 30 min avant la fermeture du délai, sinon 20 h 30 la veille), avec l'heure limite dans le push et l'email (« Tu peux le déplacer ou l'annuler dans l'app jusqu'à aujourd'hui 10:00 ») ; délai déjà fermé : téléphone du salon et « réserver un autre créneau ne supprime pas celui-ci ». Avant, le rappel « veille à l'heure du RDV » partait pile à la fermeture du délai (voir « Déplacer / annuler un RDV dans le délai »)
- **reviewReminder** : toutes les 30 min, demande d'avis 2 à 6 h après la fin d'un RDV **`confirmed` ou `completed`** passé (le salon n'utilise pas `completed` : jusqu'au 7 oct. 2026 plus rien ne partait), flag `review_reminder_sent` posé avant l'envoi
- **birthdayReminder** : tous les jours à 8 h **heure de Paris** (`timezone` node-cron, partait à 10 h avant le 7 oct. 2026), un seul envoi par jour grâce à `users.birthday_notified_on` (colonne créée par le job au démarrage), rattrapage au démarrage entre 8 h et 21 h, 29 février fêté le 28
- **mediaCleanup** (déployé le 5 sept. 2026, release v81) : tous les dimanches à 3h30 heure de Paris, supprime les images de la table `media` que plus aucune colonne ne cite (délai de grâce de 7 jours). Voir `jobs/mediaCleanup.js` et `cleanup-media.js`
  - **Incident corrigé le 25 sept. 2026 (backend v91, commit 4957528)** : le job ignorait les colonnes d'images ajoutées après lui (`products.images`, `textile_drops.cover_image_url`, `textile_concepts.images`, `salon_events.cover_image_url`, `salon_events.images`) et les a prises pour des orphelines. **6 images supprimées**, très probablement au passage du dimanche 20 sept. : couverture du drop « FIGURINE ULTRA », 1 photo du modèle « FIGURINE ULTRA », 3 photos du modèle « ASTRA », couverture de l'événement « Poker gang ». **Aucune sauvegarde Heroku n'existait** : ces images ne seront **pas** renvoyées : le client a retiré volontairement les contenus concernés (13 oct. 2026), rien à faire. Les colonnes JSONB sont lues avec `::text`, 13 colonnes protégées au départ (16 au 17 oct. 2026 : `orders.items`, `feedbacks.screenshot_url`, `employees.gallery`) (tous les endroits où l'app envoie un fichier, `partners.*` compris), et un test (`test/test-cleanup-media.js`, 21 vérifications) échoue si une colonne d'image déclarée dans `server.js` / `init-db.js` n'est pas protégée. **Règle : toute nouvelle colonne qui stocke une URL d'image doit être ajoutée à `jobs/mediaCleanup.js`**
- **comebackReminder** (déployé le 3 sept. 2026, release v68) : tous les jours à 10h heure de Paris, relance « Ça fait N semaines, on te refait ça ? » (push `sendPushToEmail` + email `sendComebackReminder`, lien `/booking?barber=<employee_id>`) aux clients `role = user` dont le dernier RDV `completed` date de plus de `salon_settings.comeback_weeks` semaines (défaut 5, modifiable par l'admin via `SalonSettings.update`) et qui n'ont aucun RDV `confirmed` à venir. Une seule relance par visite : flag `appointments.comeback_reminder_sent` sur ce dernier RDV. Une requête SQL (CTE `DISTINCT ON`), rattrapage au démarrage entre 10h et 12h. Test : `heroku run "node jobs/comebackReminder.js --dry-run" --app dhomebarber-api` (l'argument doit être entre guillemets, sinon la CLI Heroku avale `--dry-run`). Le tutoiement est voulu (ton du push)

### Fenêtre d'activation des notifications (ajoutée le 12 oct. 2026)
- `src/components/shared/NotificationPrompt.jsx`, montée dans `ClientLayout` **et** `AdminLayout` (le staff reçoit aussi des pushs) : bottom sheet « Ne rate rien du Gang » (rappel la veille, last minute, drops et événements) avec **Activer les notifications** (→ `subscribeToPush()`, donc la demande système du téléphone), **Plus tard** et la croix. Affichée 2,5 s après l'arrivée, jamais sur `/booking`, `/login`, `/settings`
- État lu par `getPushPermission()` (`src/lib/pushNotifications.js` : `granted` / `denied` / `prompt` / `optout` / `unsupported`). Jamais demandée → au plus 3 affichages, 7 jours d'écart ; refusée sur le téléphone → variante « Notifications désactivées » au plus 2 fois, 30 jours d'écart, avec **Ouvrir les réglages** sur iOS (`app-settings:`) et la marche à suivre ailleurs ; accordée ou désactivée volontairement dans Paramètres (`dhb-push-optout`) → jamais. Compteurs dans `localStorage['dhb-notif-prompt']`
- Web : seulement dans l'app installée (écran d'accueil, `display-mode: standalone`), pas dans un onglet. **Règle Apple 4.5.4 : ne jamais rendre les notifications obligatoires** (toujours « Plus tard »)
- **Rattrapage (19 oct. 2026, frontend 8318da4)** : sur téléphone, autorisation accordée mais appareil toujours pas enregistré pour le compte après la synchro du lancement (6 s d'attente) → la fenêtre s'ouvre en mode « prompt » pour finir l'activation (`unregistered` : 3 fois au plus, 3 jours d'écart ; « Activer » refait `register()` sans nouvelle demande du système). Sur iPhone, les compteurs « Plus tard » sont remis à zéro une fois (`dhb-notif-prompt-ios-fix`) : l'activation n'aboutissait jamais avant le build 13. **Apps : à partir du build 14**
- Les apps des stores ne l'ont qu'avec un nouveau build natif
