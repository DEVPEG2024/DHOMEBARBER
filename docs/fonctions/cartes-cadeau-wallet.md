# Cartes cadeau : débit au comptoir, historique, suppression, Apple / Google Wallet

> Période : 17 oct. → 19 oct. 2026. Déplacé tel quel depuis `CLAUDE.md` le 20 oct. 2026 (version du commit 7738a11). Les règles à retenir sont résumées dans `CLAUDE.md` ; ce fichier garde le détail. Quand une session modifie cette fonction, elle met ce document à jour.

### Débit d'une carte cadeau au comptoir (17 oct. 2026)
- **Parcours** (Admin → Cartes cadeau → « Scanner » le QR au dos de la carte, `?scan=CODE`, ou tap sur une carte) : en tête la carte (code, bénéficiaire, solde / montant initial, validité), puis « Que paie-t-on ? » : **RDV du jour** (par défaut : RDV `confirmed` d'aujourd'hui à Paris, sans `payment_method`, avec un client, tous barbers, le plus proche de maintenant marqué « Maintenant » ; montant = `total_price` + `product_price`), **Prestations** (catalogue actif, somme) ou **Montant libre**. Montant > solde : la carte paie son solde, « reste Y € à régler au comptoir ». Confirmation en deux taps, toast « Annuler » (10 s, remet solde, statut et RDV), écran de succès
- **RDV entièrement couvert** : case « Clôturer le RDV » cochée par défaut → mêmes champs que « Valider la prestation » (`payment_method: 'carte_cadeau'`, `status: 'completed'`, `tip: 0`, `grand_total`) + « [Carte cadeau DHB-… : 35 €] » ajouté à `internal_notes`. Partiellement couvert : pas de clôture, lien vers l'agenda pour encaisser le reste
- Carte `pending` : bandeau « À valider avant de pouvoir la débiter » (la fiche reste ouverte après validation) ; utilisée / annulée / validité passée (Paris) : aucun débit. Code absent des 200 cartes chargées : recherché par son code
- **Serveur : en place depuis le 17 oct. 2026 (backend v113, voir « Endpoints spécifiques »)**, d'après `docs/backend-gift-card-debit.md` : `POST /gift-cards/:id/debit` sous `FOR UPDATE` + table `gift_card_transactions`, `…/debit/:txId/undo`, `GET /gift-cards/:id/transactions` (la section Historique n'apparaît qu'avec elle). **Toute erreur de ces routes doit porter un `code`** : un 404 sans `code` = route absente → repli `GiftCard.update` après relecture de la carte (pas de verrou, pas d'historique). Code : `src/lib/giftCardDebit.js`, `src/components/giftcards-admin/`

### Historique et suppression définitive des cartes cadeau (18 oct. 2026, backend v127 / 6242b4f, frontend c785506, demande du propriétaire)
- **Vie de la carte** : table `gift_card_events` (voir les entités) remplie par `routes/entities.js` après une modification de `GiftCard` par l'admin (`cardEventForUpdate` / `recordCardEvent` de `lib/giftCardDebit.js`, jamais bloquant) : rejet (pending → expired), annulation (validated → expired, solde perdu), prolongation (`valid_until` changé sans changement de statut). La commande et la vente se lisent sur la carte (`created_at`, `validated_at` / `validated_by` / `payment_method`), les mouvements de solde sur `gift_card_transactions`. Une carte annulée avant le 18 oct. n'a pas d'événement : « date non notée »
- **Fiche** (`GiftCardHistory.jsx`, `buildGiftCardTimeline` de `src/lib/giftCardDebit.js`) : historique de bout en bout, plus récent d'abord (commande, vente, débits, débits annulés, rendus sur la carte, prolongation, annulation), 15 lignes puis « Afficher tout », aussi pour une carte en attente ; actions des débits inchangées (annuler 24 h, rattacher, rendre). `GET /gift-cards/:id/transactions` renvoie `events` à l'admin seulement
- **Onglet « Historique »** (`GiftCardJournal.jsx`, `?tab=history`) : `GET /gift-cards/journal?limit=&before=` (admin, 300 lignes max par page, `{ entries, has_more }`, horodatages sans fuseau de `gift_cards` lus en UTC), regroupé par jour de Paris, filtres Ventes / Utilisations / Annulations / Commandes, tap = fiche de la carte
- **Suppression définitive** (`GiftCardDeletePanel.jsx`, toute carte, payée ou non) : `GET /gift-cards/:id/deletion` (aperçu : nombre de mouvements, vente retirée du CA, RDV payés par la carte) puis `DELETE /gift-cards/:id?expect=<mouvements vus>` (admin, 409 `changed` si un mouvement est arrivé entre-temps). Une transaction, carte puis RDV verrouillés : part carte nette (débits non annulés − crédits) retirée de `appointments.gift_card_amount`, RDV clôturé « Carte cadeau » qui n'est plus couvert **rouvert** (confirmé, sans moyen de paiement, à encaisser ; jamais un annulé / absent), repère « [Carte cadeau CODE : …] » retiré de la note, puis mouvements, événements et carte effacés. Rien n'est gardé (trace dans les journaux Heroku : `[GiftCard] Carte … supprimée par …`). **Remplace la règle du tour 2** (« une carte payée ne se supprime plus ») pour la fiche admin ; la suppression générique `GiftCard.delete` garde son 409 sur une carte payée (anciennes apps). Tests : `test/test-gift-card-delete-history.js` (16)

### Last Minute et carte cadeau dans le Wallet (17 oct. 2026)

*Extrait : seule la puce « Carte cadeau dans le Wallet » ; les puces Last Minute sont dans `docs/fonctions/reservation-rendez-vous.md`.*

- **Carte cadeau dans le Wallet** (`src/lib/walletApi.js`, `components/giftcards/WalletButtons.jsx`, fiche de carte de `GiftCards.jsx`) : boutons « Ajouter à Apple Wallet » (iPhone, iPad, Mac) / « Ajouter à Google Wallet » (Android), Google seulement sur un autre ordinateur (Windows / Linux ne savent pas ouvrir un `.pkpass`), **seulement** sur une carte validée, non expirée, avec solde, et **seulement si** le serveur annonce `features.appleWallet` / `features.googleWallet` (clé `['walletFeatures']`, tout éteint en cas d'échec). `POST /gift-cards/:id/wallet-links` → `{ apple_url, google_url }` (lien `.pkpass` public à jeton de 10 min ; lien `pay.google.com/gp/v/save/<JWT>`), ouverts par `openExternalUrl` en natif. **Serveur : Apple Wallet en service depuis le 17 oct. 2026** (backend 355f9dc, Heroku v117, variables Apple posées en v118, d'après `docs/backend-wallet.md`) : `features.appleWallet` vrai, `features.googleWallet` faux. Fichiers : `lib/wallet.js`, `routes/wallet.js`, `wallet/apple/` (icônes 29 / 58 / 87, bandes 375×144 / 750×288 / 1125×432, **aucun logo**), `scripts/wallet-smoke.js` (`--fake`, `--from-dir=`, `--no-google`, `--write` ; deux `SELECT` en base), `scripts/wallet-google-class.js`, `scripts/wallet-images.js` (régénère icônes et bandes), `test/test-wallet.js` (26). **Design du pass, v2 (18 oct. 2026, demande du propriétaire, backend 6a3aa60)** : haut du pass **vide** (ni `logoText` ni `logo*.png` : Apple n'exige que l'icône ; conséquence, sur l'Apple Watch qui n'affiche pas la bande, le pass ne porte plus de marque) ; la **bande** (`strip`) ne porte que le **grand logo du salon, net**, centré (120 pt de haut, entier même si Wallet recadre la bande à 123 pt), sur le noir de la carte, sans fondu ni texte par-dessus (`primaryFields` vides) ; **une seule ligne de champs** POUR · VALIDITÉ · MONTANT (montant initial, `currencyCode` EUR, aligné à droite) — une carte de magasin met `secondaryFields` + `auxiliaryFields` sur une seule ligne et Wallet masque les champs d'une ligne trop longue, donc pas de deuxième ligne possible et le **code** n'est plus un champ : il reste sous le QR (`altText`, comme dans l'app) et au verso ; nom de la face avant borné par une **largeur estimée** (police SF 17 pt, budget ≈ « Jean-Baptiste ») : au-delà, premier mot sinon abrégé « … », nom complet au verso ; fond rgb(17,17,17), valeurs blanches, libellés verts rgb(46,158,102) ; verso inchangé (solde et validité indicatifs, code, utilisation, message, adresse, téléphone, site). Dans l'app, le logo de la carte (recto et PDF) est `src/assets/logo-card.png` (13 Ko, importé en `?inline`, data URL) au lieu de `/logo.png` (1,5 Mo), et la capture PDF attend le décodage des images (`imagesReady`). Certificat Pass Type ID `pass.fr.dhomebarber.giftcard` (équipe 3NXH4CTJM3, WWDR G4) **valable jusqu'au 16 nov. 2027** : à renouveler avant (passé cette date, le serveur éteint seul le drapeau) ; clé, certificat et WWDR dans `~/.appstoreconnect/wallet/` (hors git, jamais affichés). Pass signé par `passkit-generator` en mode strict (le moindre avertissement fait échouer le pass), chaîne vérifiée par `openssl smime -verify` jusqu'à la racine Apple, même QR que l'app. Le corps facultatif `{ wallet: 'apple' | 'google' }` ne prépare que ce Wallet : `fetchWalletLinks(cardId, kind)` l'envoie depuis le 17 oct. 2026 (sur iPhone, Google n'est jamais contacté ; les apps natives ne l'auront qu'avec un nouveau build). **Au 17 oct., aucune carte cadeau en base** : rien d'essayé sur un vrai iPhone. **Google : en attente de l'émetteur** (console Google Pay & Wallet, compte de service `wallet-issuer@…`, accès en publication), code prêt et testé, variables à ne poser qu'après l'accès en publication. Position du salon dans le pass (`SALON_LAT` / `SALON_LNG` de `lib/wallet.js`) encore approximative. Avant la production, remplacer les logos simplifiés par les **badges officiels** Apple / Google (commentaire « PRODUCTION » dans `WalletButtons.jsx`). Notes de revue : paragraphe dans `docs/app-review-notes.md` (règle 2.5.19). À vérifier sur un vrai iPhone : l'aperçu du pass depuis l'app native (sinon plugin `PKAddPassesViewController`)

### Pass Apple Wallet tenu à jour (19 oct. 2026, backend v139 / v140)
- **Signalement** : « quand l'admin débite une carte cadeau, elle se débite bien dans l'app mais pas sur la carte du Wallet ». Cause : le pass était figé au jour de l'ajout (ni `webServiceURL` ni `authenticationToken`), donc Wallet ne revenait jamais le chercher, et sa face avant affichait le montant initial
- **Pass** (`buildApplePassJson`, lib/wallet.js) : `webServiceURL` = `<API_PUBLIC_URL>/api/wallet/passkit`, `authenticationToken` = HMAC de la clé Wallet et du numéro de série (`passAuthToken`, rien en base). Face avant **POUR · VALIDITÉ · SOLDE** (remplace MONTANT du design v2 : le solde ne périme plus), solde en texte (« 35 € », « 35,50 € », largeur connue : un solde plus large que « 500 € » réduit d'autant le budget du nom), `changeMessage` « Nouveau solde : %@ » (annoncé sur l'écran verrouillé) et « Carte cadeau valable jusqu'au %@ » ; montant initial au verso ; `expirationDate` = fin du jour de validité (une prolongation pousse une mise à jour) ; `voided` quand la carte est vidée (`used` ou solde 0) ou annulée (statut `expired` → « Annulée ») ; carte supprimée → pass barré « Supprimée » sans QR, code ni nom (`buildDeletedApplePassJson`). Toujours sans `locations`
- **Service web PassKit** (`routes/walletUpdates.js`, sans session, jeton du pass dans `Authorization: ApplePass …`, 300 req / 15 min / IP) : `POST /api/wallet/passkit/v1/devices/<appareil>/registrations/<Pass Type ID>/<série>` `{ pushToken }` → 201 / 200 (401 jeton faux ou carte absente, 403 au-delà de 20 appareils), `DELETE` même chemin → 200, `GET …/devices/<appareil>/registrations/<Pass Type ID>?passesUpdatedSince=<étiquette>` → `{ serialNumbers, lastUpdated }` ou 204, `GET …/passes/<Pass Type ID>/<série>` → pass signé avec `Last-Modified` (jamais de 304 : la date HTTP est à la seconde), `POST …/log` → 200 (codes masqués)
- **Push** (`notifyPassChanged`, lib/walletUpdates.js) : version du pass avancée, puis push **vide** (`{}`) à chaque appareil, sur **APNs production** avec le **certificat Pass Type ID** en TLS client (pas la clé .p8 de l'app), `apns-topic` = `pass.fr.dhomebarber.giftcard` ; jeton refusé (410, `BadDeviceToken`, `Unregistered`) → appareil oublié. `refreshWallets(db, cardId)` (Google + Apple, jamais bloquant) est appelé après débit, annulation de débit, crédit (routes/giftCardDebit.js), toute modification `GiftCard` par l'admin (validation, annulation, prolongation, entities.js) et la suppression définitive (`{ deletedCard }`). Ce sont les seules écritures de solde (`UPDATE gift_cards` de lib/giftCardDebit.js)
- **Vérifié** : certificat accepté par APNs production avec ce sujet (faux jeton → `BadDeviceToken`) ; 14 requêtes passées en `EXPLAIN` sur la base (tables créées dans une transaction annulée) ; en production, `heroku run "node scripts/wallet-passkit-smoke.js <id de carte>"` (faux appareil enregistré, liste, pass relu et signé avec « 30 € », 401 sans jeton, push refusé pour le faux jeton puis appareil oublié, nettoyage) : tout OK, tables vides ensuite. Tests : `test/test-wallet-updates.js` (12), `test-wallet.js` adapté (26) ; `npm test` → 85 harnais
